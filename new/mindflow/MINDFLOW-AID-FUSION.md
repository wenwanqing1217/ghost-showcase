# MindFlow × AID 融合方案

## 一、项目全景

你手上实际有三个项目：

| 项目 | 定位 | 角色 | 技术栈 |
|------|------|------|--------|
| **AID（Alpha-ID）** | 数字身份基础设施 | "你是谁" — DID + 记忆 + Ghost Layer | Python |
| **MindFlow** | AI Agent 工作流平台 | "帮你做什么" — Agent 编排 + 任务执行 | TBD |
| **校园盲盒小程序** | 毕业设计/应用场景 | 第一个集成客户 + 展示Demo | 小程序/JS |

**核心关系**：
```
AID（身份层）
    ↓ DID 注入
MindFlow（执行层）
    ↓ API 调用
校园盲盒小程序（应用层）
```

---

## 二、为什么这个组合能打

### 当前市场的空白

| 产品 | 解决了什么 | 没解决什么 |
|------|-----------|-----------|
| **Dify / Coze / n8n** | 工作流自动化 | 没有数字身份层，Agent 不知道"替谁干活" |
| **AutoGPT / CrewAI** | Agent 自主执行 | 没有持久身份，每次对话都是新 Agent |
| **AID（你）** | 数字身份 + 记忆 | 没有执行层，只能"认识你"，不能"帮你做事" |
| **MindFlow（新）** | Agent 工作流编排 | 没有身份层，Agent 没有持续记忆 |

**你的独特定位**：
> **全球唯一一个把数字身份层（DID）和 Agent 执行层（工作流）打通的项目。**

### 差异化优势

| 维度 | 传统 Agent 平台 | AID × MindFlow |
|------|----------------|----------------|
| Agent 身份 | 无身份 / 临时会话 | DID 持久身份，跨会话记忆 |
| 多 Agent 协作 | 不知道替谁干活 | I2I（Identity to Identity），知道为谁服务 |
| 用户主权 | 数据锁在平台 | 私钥本地，身份可移植 |
| 工作流 | 静态脚本 | 动态适应，基于用户画像个性化 |
| 记忆 | 单次对话上下文 | 三层记忆 + 因果图谱，长期演化 |

### 数据流示例："帮我找适合送室友的盲盒"

```
1. 用户（小程序）输入："帮我找适合送室友的盲盒"
2. MindFlow 解析意图 → 生成工作流：
   [搜索 Agent] → [推荐 Agent] → [总结 Agent]
3. 每个 Agent 执行前，先向 AID 查询：
   - 用户 DID：did:aid:xxx
   - 用户画像：室友偏好（动漫/价格敏感度）
   - 历史记忆：上个月送过什么
4. Agent 基于身份信息个性化执行：
   - 搜索 Agent：筛选动漫类盲盒
   - 推荐 Agent：基于室友偏好 + 用户预算推荐
   - 总结 Agent：生成个性化推荐理由
5. 结果返回小程序，同时记录到 AID 记忆层
```

## 四、核心创新点

### 1. DID 注入的 Agent 工作流

**创新**：每个工作流执行前，都会注入执行者的 DID 身份。

```javascript
// 工作流定义
{
  "workflow": "find-gift-for-roommate",
  "agents": ["search", "recommend", "summarize"],
  "identity": "did:aid:xxx"  // ← 来自 AID
}

// Agent 执行时自动携带身份上下文
agent.execute({
  ...params,
  identity: {
    did: "did:aid:xxx",
    profile: { roommatePreferences: ["动漫", "游戏"] },
    memory: { lastGift: "动漫盲盒，2024-12" }
  }
})
```

**效果**：
- 同样的工作流，不同用户执行，结果完全不同
- Agent "知道"替谁干活，不是无状态执行

### 2. I2I（Identity to Identity）协作

**创新**：Agent 之间的协作不是简单的函数调用，而是身份到身份的交互。

```javascript
// 传统方式：Agent 不知道替谁干活
searchAgent.search("动漫盲盒")

// I2I 方式：Agent 知道为谁服务，可以向对方的 Agent 查询
searchAgent.query(
  targetAgent: "roommate-agent",
  identity: "did:aid:roommate-xxx",
  query: "喜欢什么类型的盲盒？"
)
```

**效果**：
- 模拟真实社交关系
- Agent 可以"替你做决定"，因为它知道你的社交图谱

### 3. 记忆驱动的自适应工作流

**创新**：工作流不是静态脚本，而是根据用户记忆动态调整。

```javascript
// 用户第一次执行："找送室友的盲盒"
workflow = search → recommend → summarize

// 系统记录到 AID 记忆层
memory.add({
  type: "workflow_execution",
  workflow: "find-gift",
  result: "选择了动漫盲盒",
  feedback: "用户确认购买"
})

// 用户第二次执行："找送室友的盲盒"
// 系统从记忆层读取历史，自动调整
workflow = search → recommend(基于上次偏好) → summarize → remind("上个月送过动漫盲盒，这次换个类型？")
```

## 五、技术栈建议

### MindFlow（Agent 工作流平台）

| 层级 | 推荐 | 理由 |
|------|------|------|
| **后端** | **Node.js + Fastify** | 与 AID 的 AI 代码同语言，可复用 aiService 逻辑 |
| **前端** | **Next.js + React** | 成熟生态，SSR，部署方便 |
| **工作流引擎** | **自研轻量引擎** | 先做顺序执行，后期可升级为 DAG |
| **AI 运行时** | **LangGraph / 自研** | LangGraph 成熟，但初期可自己实现简单版 |
| **数据库** | **PostgreSQL + Redis** | 关系数据 + 缓存 |
| **部署** | **Railway / Vercel** | 一键部署，适合快速验证 |
| **AI 模型** | **豆包 API（复用 AID）** | 已配置好，直接使用 |

### AID 侧需要做的适配

| 改动 | 说明 | 工作量 |
|------|------|--------|
| **新增 MindFlow 集成模块** | 提供 DID 查询、记忆查询、I2I 协议接口 | 2-3 天 |
| **定义工作流身份协议** | 工作流执行时的身份注入格式 | 1 天 |
| **记忆层扩展** | 新增工作流执行记忆类型 | 1 天 |

### 校园盲盒小程序侧

| 改动 | 说明 | 工作量 |
|------|------|--------|
| **新增 AI 助手页面** | 调用 MindFlow API | 2-3 天 |
| **DID 登录集成** | 用 AID 的 DID 登录 MindFlow | 2 天 |

## 六、MVP 执行计划

### Phase 0：AID 适配（1 周）

**目标**：让 AID 能为 MindFlow 提供身份和记忆服务

**任务清单**：
1. 在 AID 的 `core/` 模块新增 `identity-provider`（提供 DID 查询接口）
2. 在 AID 的 `entrypoints/` 新增 `api/` 路由（FastAPI 暴露 HTTP 接口）
3. 定义工作流身份协议（JSON Schema）
4. 部署 AID API 服务（本地 / Railway）

**交付物**：
- AID API 服务运行在 `localhost:8000`
- 接口文档（DID 查询、记忆查询、I2I 协议）

### Phase 1：MindFlow 核心引擎（2 周）

**目标**：能用自然语言创建并执行简单工作流

**任务清单**：
1. 初始化项目（Next.js + Fastify）
2. 实现 LLM 网关（复用 AID 的 aiService 逻辑）
3. 实现工作流引擎（JSON 定义 + 顺序执行）
4. 实现工具节点（search、recommend、notify）
5. 实现 DID 身份注入（调用 AID API）
6. 简单前端（输入框 + 结果展示）

**预设工作流模板**：
- "帮我找适合送室友的盲盒"
- "今天有什么订单要送？"
- "推荐点好玩的"

**交付物**：
- Web 界面，可以输入自然语言并看到结果
- 工作流在后台执行，携带用户 DID

### Phase 2：校园小程序集成（1 周）

**目标**：AID 小程序可以调用 MindFlow

**任务清单**：
1. 小程序新增"AI 助手"页面
2. 调用 MindFlow API
3. 展示工作流执行结果

**交付物**：
- 小程序里有一个能说话的 AI 助手

### Phase 3：工作流可视化（2 周）

**目标**：用户可以查看、编辑、分享工作流

**任务清单**：
1. 工作流列表页（历史执行记录）
2. 简单的工作流编辑器（JSON 编辑或模板化）
3. 工作流导入/导出

### Phase 4：平台化（1-2 个月）

**目标**：多用户、工作流市场、开放 API

**任务清单**：
1. 用户注册/登录
2. 工作流市场
3. 多租户隔离
4. API 开放

## 七、利弊分析

### 方案优势

| 优势 | 说明 |
|------|------|
| **差异化明显** | 全球唯一 DID + Agent 工作流融合项目 |
| **代码复用率高** | AID 的 LLM 逻辑、记忆层可直接复用 |
| **技术栈统一** | 都用 Node.js/Python，学习成本低 |
| **有真实场景** | 校园盲盒小程序作为第一个客户 |
| **长期价值高** | 可以作为开源项目、论文、创业起点 |
| **省事儿** | 不用从零开始，增量开发 |

### 潜在风险

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| AID API 服务稳定性 | 中 | 中 | 本地 fallback，AID 挂了 MindFlow 仍可降级运行 |
| 工作流复杂度失控 | 中 | 高 | Phase 1 只做顺序执行，不做 DAG |
| 大模型 API 成本 | 中 | 中 | 做缓存、限制频率、用便宜模型 |
| 没有真实用户 | 高 | 中 | 自己用 + 开源展示 + 校园小程序集成 |

## 八、与之前方案的区别

| 维度 | 之前的 MindFlow | 现在的融合方案 |
|------|----------------|--------------|
| 定位 | 独立的 AI 工作流平台 | **AID 的 Agent 执行层** |
| 身份 | 无身份概念 | **DID 注入，I2I 协作** |
| 记忆 | 无持久记忆 | **AID 三层记忆驱动** |
| 差异化 | 一般（跟 Dify/Coze 类似） | **极高（全球唯一）** |
| 与 AID 关系 | 无关 | **深度集成，互为补充** |
| 数字孪生 | 自己做 | **交给 AID，MindFlow 专注执行** |
