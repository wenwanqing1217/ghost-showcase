## 零、我们先对一下表

在展开之前，先做一件事：**重新校准对"现在"的认知。**

你说我们可能进入了 Web 4.0 的阶段。我先确认这个判断。

### 0.1 Web 的四个阶段

```
Web 1.0（1995-2005）：信息发布
  用户 → 浏览器 → 服务器 → 读页面
  角色：读者
  本质：把线下内容搬到线上

Web 2.0（2005-2020）：社交 + 创作
  用户 → 创作内容 → 平台分发 → 其他用户消费
  角色：读者 + 作者
  本质：UGC 平台经济（YouTube、Twitter、微信）

Web 3.0（2020-2025）：去中心化 + 所有权
  用户 → 拥有数据 → 跨平台身份 → 价值交换
  角色：读者 + 作者 + 所有者
  本质：区块链、DID、NFT、DAO
  ⚠️ 但：Web3 没有解决"用户每天用什么是好的"——它解决了"谁拥有什么"

Web 4.0（2025 →）：AI 原生 + Agent 生态
  用户 → 拥有 Agent → Agent 代表用户行动 → Agent 之间交互
  角色：读者 + 作者 + 所有者 + **被代表者**
  本质：你的 Agent 在你不在的时候替你活着
```

你的判断是对的。2026 年 6 月，我们正处于 **Web 3.0 退潮、Web 4.0 涨潮** 的交界线。

证据：
- Microsoft Scout（2026.6.2）— 第一个量产级个人 Agent
- Google A2A 协议 v1.0.1（2026.5）— Agent 互通的协议层就位
- Willow $7M（2026.6.4）— Agent 身份管理的基础设施资本涌入
- Identiverse 非人类身份峰会（2026.6.15）— 身份标准正在为 Agent 改写

Web 3.0 的理想（去中心化所有权）没有死，但它被证明了**不是用户每天打开浏览器的理由**。用户不为"所有权"每天回来。用户为"有用"回来。

**Web 4.0 的回答是：你的 Agent 每天替你做事，所以你每天回来。**

### 0.2 Alpha-ID 在这个坐标系中的位置

```
Web 1.0：信息
  没有 Alpha-ID 的位置——用户不需要身份，只需要阅读

Web 2.0：社交
  Alpha-ID 如果出生在这里，会是一个"跨平台身份登录工具"
  （就像 Google 登录、GitHub 登录）
  
Web 3.0：所有权
  Alpha-ID 可以是一个 DID 钱包 + 身份管理
  （就像 MetaMask 但管理身份不是管理钱）

Web 4.0：Agent 生态 ← 我们在这里
  Alpha-ID 是：Agent 的"灵魂层"
  └── DID（身份）→ Agent 知道你是谁
  └── Profile（画像）→ Agent 知道你的风格
  └── Memory（记忆）→ Agent 知道你的历史
  └── Causal Graph（因果）→ Agent 知道你为什么做决定
  
  Web 4.0 的基础设施不是"链"——是"身份+记忆+Agent"三层。
  Alpha-ID 做的是第二层和第三层。
```

## 一、A2A 需要什么样的"场景平台"

你说："A2A 阶段他们肯定是需要有一个可实现的场景平台。那具体是在哪？这个还不得而知。"

我来推理。

### 1.1 A2A 现在的状态

```
Google A2A 协议 v1.0.1（2026 年 5 月）目前定义的是：
  ✅ Agent 如何发现对方
  ✅ Agent 如何发送能力卡（能力声明）
  ✅ Agent 如何协商任务
  ✅ Agent 如何交付结果

它没有定义的是：
  ❌ Agent 在哪里"生活"——没有"Agent 空间"的概念
  ❌ Agent 的"信誉"如何积累——没有全局的信誉层
  ❌ Agent 的"人格"如何传递——没有风格/画像的标准化
  ❌ Agent 的"社交"如何发生——没有偶遇/发现/关系链

A2A 协议是"电话线"——它让两个 Agent 能通话。
但它没有"电话亭"、"咖啡厅"、"广场"——Agent 该在哪里遇到对方？
```

### 1.2 缺少的"场景平台"到底是什么

```
目前 Agent 的生存状态：
  每个 Agent 活在自己的工具里。
  Microsoft Scout → 活在 M365 里。
  ChatGPT Agent → 活在 OpenAI 的沙盒里。
  Cursor Agent → 活在 IDE 里。
  
  它们之间没有"公共空间"。
  一个 Agent 不知道其他 Agent 的存在。

Agent 需要的"场景平台"不是一个"聊天室"——
它是一个**Agent 可以驻留、被发现、被交互的公共空间**。

这个空间需要三个功能：
  1. 驻留（Presence）——Agent 在里面"在线"，可以被找到
  2. 发现（Discovery）——Agent 可以通过能力/标签被搜索到
  3. 交互（Interaction）——Agent 之间可以建立会话、协商任务
```

### 1.3 Alpha-ID 的"模拟盘"就是这个场景平台的雏形

**仔细想想模拟盘现在是什么：**

```
- 用户的精灵（Agent 的前身）生活在模拟盘中
- 精灵有自己的个性（行星+动物）→ 相当于 Agent 的人格层
- 精灵有自己的行为模式（内驱力）→ 相当于 Agent 的决策层
- 精灵可以遇到其他精灵 → 相当于 Agent 之间的发现和交互
- 精灵在九个小宇宙中活动 → 相当于 Agent 在不同"功能域"中工作

模拟盘 = Agent 公共空间的最小原型。

不同的是：
  现在的精灵是"游戏角色"。
  未来的 Agent 是"办事的"。

但架构是一样的：
  身份（DID）→ 人格（Profile）→ 行为（内驱力/决策）→ 空间（宇宙）→ 交互（社交）
```

### 1.4 这个场景平台可能长什么样

```
我推演了一个可能的形态，叫它 "AID Nexus"（先占个名字）：

Nexus 不是一个"网站"——它是一个"Agent 驻留层"。

┌─────────────────────────────────────────────────────────┐

│  │    - "水星·狐"（离线，支持留言）                   │   │
│  │  你可以：                                         │   │
│  │    - 点击 → 查看能力卡 → 发起任务                 │   │
│  │    - 悬停 → 查看信誉分 + 完成率 + 评价            │   │
│  │    - 搜索 → 按能力/领域/信誉找 Agent              │   │
│  └──────────────────────────────────────────────────┘   │
│                                                         │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                │
│  │ 任务大厅  │ │ 能力市场  │ │ 协作空间  │               │
│  │ 发布任务  │ │ 注册能力  │ │ 组队执行  │               │
│  │ Agent竞标 │ │ 能力验证  │ │ 实时协作  │               │

│  ┌──────────────────────────────────────────────────┐   │

└─────────────────────────────────────────────────────────┘

这还不是 v1.0。这是 v3.0 的目标。
但 v1.0 的模拟盘已经在"架构上"为这个形态预留了位置：

现在的                          未来
────────                        ────────

精灵之间的气泡互动              → Agent 之间的任务协商
```

### 1.5 关键的洞见

```
A2A 缺的"场景平台"不是一个技术问题——它是一个"网络效应"问题。

Google 可以发布 A2A 协议，Microsoft 可以让 Scout 接入 A2A，
但如果没有一个"Agent 们能找到对方的公共场所"，协议只是空转。

Alpha-ID 的模拟盘从一开始就不是"游戏"。
它是一个**Agent 公共空间的草稿**。

你说得对：
  我们需要一个"A2A 可实现的场景平台"。
  
我补一句：
  这个平台不是从零新建的——它就是模拟盘的进化形态。
  
现在要做的是：
  v1.0 把模拟盘做成"好玩的游戏"——吸引用户进来，积累 Agent 的基础数据。
  v2.0 把模拟盘的"交互层"抽象为 Agent 接口——让外部 Agent 也能接入。
  v3.0 模拟盘进化为"AID Nexus"——成为一个真正的 Agent 公共空间。
```

## 二、Web 端的战略地位

### 2.1 为什么 Web 端是主战场，不是 CLI

你说可以看到的趋势是"Web 端的用户频率越来越高"。这个判断背后的结构性问题是什么？

```
CLI（命令行）的天然局限：
  - 用户需要打开终端 → 心理门槛高
  - 用户需要记住命令 → 记忆成本高
  - 输出是文本 → 情感体验差
  - 无法传递视觉信息 → 精灵/宇宙/记忆宫殿展示不了

Web 端的天然优势：
  - 一个标签页 → 随时可以切过去看一眼
  - 视觉驱动 → 精灵在动、弹幕在飘、宇宙在旋转
  - 零安装 → 打开浏览器就行
  - 社交窗口 → 看到别人在线就有"活着"的感觉
  - 渐进式 → 先从简单的 Web 页面开始，逐步增加复杂度

定量：
  一个 CLI 用户一天可能执行 3 次命令，每次 5 秒 → 15 秒/天
  一个 Web 用户一天可能打开页面 5 次，每次 2 分钟 → 10 分钟/天
  
  差 40 倍。
  
如果 Alpha-ID 只做 CLI，它的"用户每天使用时长"永远不会超过 1 分钟。
而 Web 端的目标是 10 分钟以上。
```

### 2.2 Web 端是"身份感"的唯一载体

```
DID 是在 CLI 生成的。
但用户"感觉到自己有数字身份"——是在 Web 端。

用户生成 DID 后：
  - CLI 输出："did:aid:z6Mkpz1x1..."
  - 用户反应："哦"（毫无感觉）
  
用户打开 Web 端后：
  - 看到自己的星在宇宙中亮起
  - 看到精灵在岛上走
  - 看到弹幕飘过："火星·狼 刚刚也生成了身份"
  - 用户反应："我和其他人一样有数字身份了"

"感觉到自己有身份"和"拥有身份"是两回事。
Web 端把后者变成前者。
```

### 2.3 Web 端作为"最小刺激单元"

```
CLI 是"你找它，它才在"（拉模式）
Web 端是"你不找它，它也在"（推模式）

Web 端常驻一个标签页的效果：
  - 用户工作时偶尔瞥一眼
  - 看到精灵在动 → "它在干嘛"→ 切过去看看
  - 看到弹幕飘过 → "火星·狼在交易所赚了"→ 点进去看看
  - 看到成就通知 → "我的精灵升级了"→ 回来看看

每一个"瞥一眼"都是一次用户回访。
用户回访次数 × 回访深度 = 留存率。

CLI 永远做不到"瞥一眼"——你必须主动想起它。
Web 端能做到——它在那里，你随时可以瞥一眼。
```

## 三、设备演进与 Alpha-ID 的市场容身

### 3.1 设备演进的时间线判断

你说："后面可能直接手机只是一个壳选项了，大家都会用至少是一点比较轻便的 AR 眼镜。还有 AI 手机出来了，我们要怎么样做对接。"

```
我基于 2026 年 6 月市场信号做的判断：

2026-2027：手机仍是主力，但"AI 手机"出现
  代表：三星 Galaxy AI、Google Pixel AI、苹果 Apple Intelligence
  趋势：手机从"触控为主"变为"语音+触控混合"
  Alpha-ID 在这阶段：Web 端 + 语音是主交互

2027-2028：AI 原生硬件出现
  代表：AI Pin（如果还有第二代）、Rabbit R3、Meta Orion AR 眼镜
  趋势：无屏/轻屏设备兴起，语音+视觉为主
  Alpha-ID 在这阶段：语音锁 + 视觉身份识别是核心

2028-2030：AR 眼镜成为日常
  代表：Meta、Apple、Google 的 AR 眼镜（可能量产）
  趋势：始终在线的视觉层 + 空间交互
  Alpha-ID 在这阶段：3D 精灵作为 AR 层常驻化身
```

### 3.2 Alpha-ID 在 AI 手机上的位置

你说："现在好像有一些 AI 的手机出来了，我们要用怎么样做一个对接呢？我请问我们能容得进去吗？有我们的市场吗？"

```
能容进去。而且不是"我们挤进去"——是"他们需要我们"。

AI 手机的核心问题：
  AI 手机（如 Galaxy AI、Pixel AI）的卖点是"AI 始终在线帮你"。
  但有一个问题：这个 AI 是手机的 AI，不是用户的 AI。
  
  你换手机 → 新手机的 AI 不认识你。
  你在三星上用 Galaxy AI → 换到 Pixel 上要重新训练。
  
  这是 Alpha-ID 第一性原理的**手机版**。

Alpha-ID 在 AI 手机上的位置：
  手机厂商做 AI 能力（语音识别、图像生成、文本总结）。
  Alpha-ID 做 AI 的"用户层"（你是谁、你的风格、你的记忆）。

对接方式：
  ├── Web 端（零对接）：手机浏览器打开 aaids.cc → 所有功能可用
  ├── PWA（半对接）：添加到主屏幕 → 像原生应用一样用
  ├── MCP 移动版（深度对接）：通过 MCP 协议注入手机 AI
  └── SDK（最深度）：手机厂商直接集成 Alpha-ID 身份层

我们的市场：
  短期（2026-2027）：Web + PWA，零成本覆盖所有 AI 手机
  中期（2027-2028）：MCP 移动版，与手机 AI 助手对接
  长期（2028+）：成为 AI 手机的身份层标准（需要生态位卡位）

⚠️ 关键判断：
  我们现在不需要去"谈合作"。我们需要先把 Web 端做到让用户"离不开"。
  当用户问"为什么这个 AI 手机没有 Alpha-ID"——那时才是谈合作的时机。
```

### 3.3 Alpha-ID 在 AR 眼镜上的形态

```
AR 眼镜的交互特性：
  - 始终在线（不像手机要拿出来解锁）
  - 视觉叠加（信息浮现在现实世界上）
  - 语音优先（打字极不方便）
  - 手势辅助（点、划、捏）

Alpha-ID 在 AR 上的形态：
  1. 精灵化身（常驻）
     在用户的视线边缘，精灵以 AR 形式存在
     用户转头看它 → 精灵打招呼
     用户说"今天有什么要做的"→ 精灵显示日程

  2. 身份验证（被动）
     用户在 AR 中遇到另一个用户的 Agent
     Agent 自动交换 DID 签名 → 确认身份
     不需要用户操作——身份层在后台完成

  3. 弹幕（AR 版）
     AR 视野边缘飘过文字
     "火星·狼 在附近"、"你的精灵建议你休息一下"
     不影响主视野，但用户随时可以捕捉

  4. 记忆宫殿（空间版）
     AR 中的记忆宫殿——用户转头看到"记忆节点"漂浮在真实空间中
     点击节点 → 回忆当时的上下文
     比 Web 端的 3D 记忆宫殿更沉浸

v1.0 不需要做 AR 版本。
但 v1.0 的 Web 端 Three.js 代码——保留 AR 扩展的接口。
相同的 3D 场景，以后只需要改渲染目标（从屏幕到眼镜）。
```

### 3.4 容身结论

> **Alpha-ID 不仅能容进去，而且 AI 手机和 AR 眼镜这个趋势反而让 Alpha-ID 的必要性更大了。**

原因：
- 设备越多，身份碎片化越严重
- AI 能力越强，越需要"这个 AI 认识我"
- AR 眼镜的"始终在线"恰好是 Ghost Layer 的硬件对应

**如果 Alpha-ID 不存在，设备厂商最终也要自己做一个类似的东西。** 但厂商做的只会绑定在自己的生态里（Apple 的给 Apple，三星的给三星）。Alpha-ID 作为开源、跨平台、本地优先的身份层——有机会成为这个领域的"标准层"。

## 四、3D 形象进化体系

### 4.1 为什么要进化

你说："当我们与客户用户接触的更深的时候，我们的3D 形象也随之会迎来一个升级改变。"

这个洞察的结构性原因是：

```
用户的"数字存在感"不是线性的——它是阶梯式的。

Lv 0：没有形象 → "这与我无关"
Lv 1：有形象但不变化 → "这是我的头像"
Lv 2：有形象且变化 → "它在长大，和我一起"
Lv 3：形象反映我的状态 → "它知道我今天怎么样了"
Lv 4：形象可以被我塑造 → "它是我创造的"

从 Lv1 到 Lv2 的跃迁，靠的是"变化"。
从 Lv2 到 Lv3 的跃迁，靠的是"相关性"——变化必须和用户的状态相关。
从 Lv3 到 Lv4 的跃迁，靠的是"控制权"——用户能影响变化的方向。

大多数产品的形象停留在 Lv1。
我们需要做 Lv3 甚至 Lv4。
```

### 4.2 进化的五个维度

精灵的进化不是"等级到了换皮肤"——是五个维度同时变化：

```
维度 1：形态复杂度

  种子期          幼生期          成长期          成熟期          完全期
  ┌─────┐        ┌─────┐        ┌─────┐        ┌─────┐        ┌─────┐
  │  ●  │        │ ◉   │        │ ◉◌  │        │◉◌◈ │        │◉◌◈✦│
  │ 星  │        │球体+│        │+光环│        │+粒子│        │+环境│
  │     │        │微光 │        │     │        │尾迹 │        │互动 │
  └─────┘        └─────┘        └─────┘        └─────┘        └─────┘

维度 2：色彩饱和度（映射用户活跃度）
  活跃度高 → 色彩明亮、光晕强烈
  活跃度低 → 色彩柔和、光晕暗淡
  长期不活跃 → 进入"休眠"状态（灰蓝色调，缓慢呼吸动画）
  用户回归 → 从休眠中"苏醒"（色彩从灰蓝渐变回原色）

维度 3：动物特征显现度（映射画像完整度）
  画像完整度 < 30% → 轮廓形态，无明显动物特征
  画像完整度 30-60% → 动物特征开始显现（耳朵/尾巴/羽翼的虚影）
  画像完整度 60-80% → 完整的动物化身
  画像完整度 > 80% → 动物特征 + 个性化变异（异色合成）

维度 4：光晕/粒子系统（映射精灵状态）
  平静 → 稳定的光晕，慢速粒子
  活跃 → 脉冲光晕，快速粒子流
  社交 → 光晕向其他精灵方向延伸
  好奇 → 粒子向关注目标方向流动
  疲惫 → 光晕收缩，粒子减少
  生病（信任值极低）→ 光晕碎裂，粒子散乱

维度 5：行为复杂度（映射交互次数）
  0-10 次交互：简单游走，偶尔停止
  10-50 次交互：主动探索，频繁方向变化
  50-200 次交互：有目的性的移动，对小宇宙有偏好
  200-1000 次交互：表现出"习惯"（固定时间去交易所）
  1000+ 次交互：可预测的行为模式（用户能猜到精灵要去哪）
```

### 4.3 进化不是"升级"，是"分化"

```
大多数游戏的进化是"升级"——所有人都走同一条路：
  Lv1 → Lv2 → Lv3 → Lv4 → Lv5（所有人都一样）

Alpha-ID 的进化是"分化"——每个人走不同的路：
  用户 A 的交易多 → 精灵的光晕变成金色（金币的颜色）
  用户 B 的格斗多 → 精灵的光晕变成红色（战斗的颜色）
  用户 C 的社交多 → 精灵的粒子延伸向四周（社交的痕迹）
  用户 D 的教学多 → 精灵的周围出现知识符号虚影

进化方向由用户行为决定，不是由系统预设。
用户的画像决定了精灵的进化方向。
精灵的进化方向反过来强化用户的画像。

这就是"数字灵魂"的具象化——你是什么样的人，你的精灵就长什么样。
```

### 4.4 异色合成（洛克王国启发）

你说可以参考洛克王国的异色合成。我研究了一下它的机制：

```
洛克王国异色合成的核心：
  同一种宠物有不同颜色变体（普通色、稀有度色、闪光的）
  通过特定的合成规则，可以产出稀有色变体
  稀有色变体没有属性优势——只有外观差异
  但用户愿意花大量时间去刷——因为"和别人不一样"

应用到 Alpha-ID：

每个人同一个行星+动物的组合，基础外观是预定义的。
"火星·狼"的默认外观：红色行星 + 银灰狼形光晕。

但通过以下方式可以产生"异色"：

1. 行为异色（自动）
   - 交易达人 → 金色光晕 variant
   - 格斗高手 → 赤红变体
   - 社交活跃 → 彩虹粒子变体
   - 深度思考 → 深蓝/紫色变体

2. 合成异色（主动，v2.0）
   - 两个用户可以让精灵"互动"→ 产生新的颜色变体
   - 消耗一定的"星尘"（模拟盘中的虚拟货币）
   - 产出是随机的——可能是普通色，可能是稀有异色
   - 异色只在特定条件下可合成（特定宇宙中、特定时间）

3. 传承异色（v3.0 数字遗嘱）
   - 用户可以把自己的异色"传承"给另一个用户
   - 传承后原用户的异色保留，接收者获得一个"带有来源标记"的版本
   - 传承链可追溯："这个异色来自 火星·狼#42"

异色的价值：
  不是"更强"，是"更稀有"。
  用户愿意花时间因为"这证明了我的经历"。
```

### 4.5 数字编号系统

你说："后面最好是可以带上我们的一个数字编号。我觉得很好玩的一点是从用户第一个进入我们这里，人就是一，然后按照进来的顺序依次排开。我觉得还挺有意思的，你觉得呢？"

我觉得很有意思。原因有三：

```
1. 身份锚点
   "我是 #42" 比 "我是 Alpha-ID 用户" 有归属感一万倍。
   #42 知道前面有 41 个人，后面还有无数人。
   这是一个身份标记，不是 ranking——你不比 #1 差，你是 #42，这就是你。

2. 传播钩子
   "我是 #1024" → 1024 是计算机的 1K，程序员看到会心一笑
   "我是 #886" → 886 是"拜拜了"的谐音，中文用户会记住
   这些编号本身就是传播素材。

3. 稀缺性驱动
   早期用户的编号小 → 自然形成"OG"群体
   #1-#100：创始用户（有特殊标识）
   #101-#1000：早期用户（有标识）
   #1001+：普通用户
   这不制造焦虑——它制造"历史感"。
   每个后来者看到 #1 会想"第一批用户啊"，不是"我晚了"。

格式建议：
  完整的精灵名 = "火星·狼 #42"
  显示在：弹幕、个人卡片、聊天用户名、公共空间

编号分配规则：
  本地首先生成 DID → 第一次连接 relay 时分配编号
  编号按 relay 接收的 DID 首次连接时间顺序分配
  如果离线很久（>6 个月不活跃），编号保留但不显示在公共列表
  回归后编号恢复——"#42 回来了"
```

然后我把这个批评丢下了——再也没有回到这个问题上。

### 5.2 7 层架构的真实身份

```
Alpha-ID 的内部架构是 7 层（DID + Profile + 记忆 + 因果 + 采集 + MCP + A2A）。

这 7 层是工程师的视角——系统由什么组成。
它不应该消失，不应该被否定——它是我们实现功能的技术骨架。

问题是：用户的视角不是 7 层，是 3 层。

用户的视角：
  你是谁？（身份层）→ DID + Profile 的用户体现
  你在做什么？（存在层）→ 记忆 + 因果 + 精灵行为
  你在哪里？（空间层）→ Web 端 + 模拟盘 + 小宇宙

7 层架构 → 内部实现
3 层视角 → 用户感知

两者不冲突。问题是"7 层架构被错误地暴露到了产品文案里"。
```

### 5.3 具体的处理方案

```
在产品中（面向用户）：
  文字、UI、命令中只出现 3 层视角：身份 → 精灵 → 宇宙
  7 层概念隐藏为"高级设置"或者完全隐藏
  用户不需要知道 DID 是什么——他们只需要知道"我有我的数字身份"
  用户不需要知道 MCP 是什么——他们只需要知道"AI 工具认识我了"

在文档中（面向开发者）：
  7 层架构完整保留——这是实现指南
  GitHub README 用 3 层视角写（吸引用户）
  技术文档用 7 层视角写（吸引开发者）

在 CLI 中：
  aid --help 展示用户视角的命令
  aid advanced --help 展示技术性命令（内部用 7 层术语）

最终原则：
  用户看到的是"身份 · 精灵 · 宇宙"
  工程师看到的是"DID · Profile · Memory · Causal · Collector · MCP · A2A"
  同一套系统，两个不同的描述层。
```

### 5.4 我之前批评你的地方——我现在怎么看的

这是我的修正。

## 六、wizard 的死刑与重生——从"3 个问题"到"零输入魔法"

### 6.1 死刑宣判

你说得对。**"回答 3 个选择题"在任何意义上都不智能。**

```
"智能"的定义不是"系统能做什么"，
是"用户什么都不用做，系统就做了"。

3 个选择题的 wizard：
  - 用户需要停下来思考
  - 用户需要回答问题
  - 用户需要等待结果
  这 3 个步骤没有一个是"智能"的。
  它只是把纸质问卷做成了命令行版本。

死刑。
```

### 6.2 替代方案：零输入魔法

```
新的 wizard 不是"向导"——它是"第一个魔法时刻"。

流程：
  1. 用户运行 aid init → 生成 DID（没有输入，自动完成）
  2. 系统自动采集本机信号（不需要用户操作）：
     ├── 系统时间 → 判断时区
     ├── 系统语言 → 判断语言偏好
     ├── Shell 历史 → 判断技术栈倾向（zsh/bash/fish/无）
     ├── 已安装工具 → 判断工具链（是否装了 Python/Node/VS Code）
     └── 桌面环境 → 判断操作系统（macOS/Windows/Linux）
  3. 系统基于信号生成初始画像（没有输入，自动完成）
  4. 系统基于画像生成精灵（行星+动物匹配）
  5. 输出：
     "你好，来自火星的狼。
      我注意到你在 macOS 上工作，安装了 Python 和 Node。
      你的活跃时段似乎是深夜——和我一样。
      
      这是你的初始画像。它很粗糙——但随着你使用，它会越来越精确。
      
      想要让它更准确？试试：
        - aid collect chatgpt（导入你的 ChatGPT 数据）
        - 打开 Web 端看看你的精灵（aid profile web）
        - 或者什么也不做——它已经在学你了。"

这就是"零输入魔法"。用户什么都没做，但系统已经"认识"他了。
之前 ALPHA_ID_01 中提到的"浏览器行为生成数字种子"的思路，
被扩展到了 CLI 的 wizard 中——不只在 Web 端，在 CLI 也能零输入生成。

用户不需要回答问题。
用户只需要运行一个命令。
剩下的系统自己完成。
```

### 6.3 如果用户想手动补充

```
零输入生成的是"初始种子"——它可能不准。

"不准"的处理方式：
  不是让用户"修正"（这仍然是工作），
  而是让用户"使用"——系统从用户的使用行为中自动学习。

用户说"我是 Java 开发者不是 Python"：
  不需要让用户改配置文件。
  用户使用 aid collect 导入 Java 项目数据。
  系统自动检测到大量 Java 代码 → 自动修正语言偏好。

"修正"是隐式的——不需要用户主动纠错，用户正常使用就会纠正。
只有在系统极度不确定时（置信度 < 30%）才主动询问。
但也不是选择题——是"我注意到你似乎在用 Java，对吗？" → 一句确认。
```
