# aid + mindflow 全板块 — 讨论纪要

> 日期：2026-07-18 ~ 2026-07-21

## 一、起点：用户痛点

用户日常使用百度地图时遇到的问题：

- 不止一个目的地，中途想办别的事，想找顺路的
- 每次都要退出重新输入目的地，转来转去记不住
- 和豆包讲又觉得多此一举
- 导航时一点返回就退出导航，没有悬浮窗
- 到了目的地之后想找附近的东西（比如24小时自助银行），地图不够智能
- 这些需求不止在地图场景，生活中各种场景都有

## 二、市场调研：现有产品分析

### 2.1 百度地图

**已有能力：**
- "智能调序"功能：添加多个途经点，系统自动优化顺序
- 支持手动添加途经点、收藏夹导入、PC端拖拽调整
- 有到站提醒、路线收藏、离线保存

**不足：**
- 顺路推荐不够智能，不理解用户当前状态（出发前/途中/到达后）
- 多目的地需要手动添加，不能一句话搞定
- 导航时没有悬浮窗模式

### 2.2 高德地图

**已有能力：**
- 最多支持24个途经点
- "顺路规划"功能
- "智能排序"自动优化路径
- 行程单功能，支持设置停留时间
- 导航中动态增删途经点

**不足：**
- 同百度地图，不理解用户场景
- 不能跨应用推荐

### 2.3 豆包导航

**已有能力：**
- 一句话启动导航
- 悬浮小窗模式
- 步行/骑行支持App内原生导航
- 实时语音播报

**缺点：**
- 导航精度差，到了目的地还提示继续走30米
- 看路能力几乎为零
- 只支持步行/骑行，驾车公交必须跳转高德
- 没有多目的地规划
- 数据全靠百度地图和高德，自己没有核心能力
- 打车接曹操出行，优惠力度远不如滴滴/高德
- 专业版68元/月，5倍额度实际用不到10次就耗尽
- 领不到平台优惠券，不是最优价格

### 2.4 千问App（阿里）

**已有能力：**
- 接入高德地图，支持顺路规划
- 可视化决策卡片，一键唤起导航或打车
- 接入淘宝、支付宝、飞猪等阿里生态
- AI订票买菜，对话框内闭环

**缺点：**
- 生态壁垒严重，只在阿里系内好用，美团微信等第三方不通
- 数据打通率仅60%，内部部门墙
- 记忆和个性化缺失
- AI幻觉严重，约90%的AI行程至少有一个错误
- 跨应用执行三成失败，验证码就卡住
- 复杂需求还是要手动确认
- 领不到券、链接失效等bug
- 说话比点击还累

### 2.5 腾讯马维斯（Marvis）

**已有能力：**
- 操作系统级操控：找文件、改设置、装软件、清C盘
- 6个AI Agent协作（文件/系统/应用/浏览器/搜索）
- 跨端操控：手机远程控制电脑，iOS/Android/Windows/Mac全覆盖
- 本地模式：隐私模式下数据完全不出电脑
- 免费，每天1000万Token

**缺点：**
- App Agent能力很弱，能打开但进去了抓瞎，微信/支付宝不支持
- 最多同时跑3个任务
- 操作速度慢
- Token消耗惊人，搜100多张图片用200万Token
- 跨端任务容易断链
- 没有出行/地图能力

### 2.6 通用AI出行助手通病

- 信息不准确：推荐已关门的店、过期的票价、不存在的航班
- 缺乏场景感知：不会根据出发前/途中/到达后推荐不同内容
- 没有真正的顺路逻辑：只按距离排，不懂当前交通方式
- 不能跨平台比价：每个AI只推自家生态
- 隐私和安全问题

## 三、核心矛盾与最优解

### 3.1 核心矛盾

```
AI助理想操控一切 ←→ 原生App不让碰 ←→ 套壳又不顶用
```

### 3.2 三条路径对比

| 路径 | 代表 | 优点 | 缺点 |
|------|------|------|------|
| 跳过原生App | 千问/豆包 | 体验丝滑 | 只能覆盖自家生态，服务深度不如原生App |
| 在原生App上操控 | 马维斯 | 用原生App体验完整 | 不稳定、维护成本高、隐私风险 |
| 衔接层（更优解） | aid的路径 | 原生App体验+跨App比价+低维护成本 | 部分App的URL Scheme支持有限 |

### 3.3 最优解：编排用户与App之间的交互

**助理不是App的操控者，是App之间的编排者。App负责执行，助理负责思考和衔接。**

三层衔接深度：

1. **URL Scheme跳转**（所有App支持）：拼好链接跳转App
2. **Deep Link精准直达**（主流App 80%+支持）：跳转特定页面，信息预填好
3. **API直连+App内展示**（需要合作）：在aid内直接展示结果，确认后跳转执行

## 四、为什么大厂不做衔接层

1. **商业模式冲突**：帮用户去竞品等于自杀
2. **数据护城河逻辑**：开放数据等于自毁
3. **投资人不答应**：帮别人导流没有商业闭环
4. **组织架构做不了**：内部部门墙锁死了开放衔接

**大厂不碰这一步不是没想到，是碰不了。它们的生态护城河恰恰是它们的牢笼。aid没有牢笼，所以能做那个"站在所有App之间"的人。**

## 五、aid + mindflow 架构

### 5.1 架构定位

```
aid（脑）= 数字孪生 = 知道你是谁、你要什么、你的习惯
mindflow（手和脚）= Agent执行层 = 知道怎么帮你做、怎么衔接各个App
```

### 5.2 出行板块核心能力

1. **多目的地顺路规划**：输入所有目的地，智能排路线
2. **场景感知推荐**：出发前/途中/到达后，根据状态推荐不同顺路选项
3. **跨App聚合比价**：同时调多个API，看清最优选择
4. **一键跳转执行**：Deep Link预填好信息，跳原生App确认即可

### 5.3 不做什么

- 不自建地图/导航
- 不操控App内部
- 不绑死一个生态

### 5.4 差异化壁垒

大厂做不了——不能往竞品导流、不能开放数据、组织架构锁死。aid没有生态包袱，能站在所有App之间。

## 七、数据策略

### 7.1 核心原则：数字孪生不是建出来的，是长出来的

```
有一个"够用"的孪生 → 开始服务用户 → 使用中产生干净数据 → 孪生越来越准
```

### 7.2 三层数据架构

| 层级 | 数据类型 | 来源 | 干净程度 |
|------|---------|------|---------|
| 第一层：锚点数据 | 日程/常去地点/出行偏好 | 用户主动给 | 100% |
| 第二层：行为数据 | 出行轨迹/点击选择/跳转记录 | 使用中产生 | 80% |
| 第三层：脏数据参考 | 历史定位/碎片信息 | 被动感知 | 当假设不当事实 |

### 7.3 脏数据策略

- 脏数据当"假设"，不当"事实"
- 用脏数据触发确认："你是去那个常去的写字楼吗？"
- 确认后就是干净数据

### 7.4 本地提取结论，只传结论

```
aid装在每台设备上 → 本地扫描提取结论 → 只传结论回aid → 原始数据不出设备
```

- 不采集原始数据
- 不需要清洗
- 不需要销毁
- 从第一天就不存原始数据

## 八、aid唯一性与设备绑定

### 8.1 核心设计

- aid具有唯一性，像身份证或电话号码
- 一个人就一个aid
- 不可能一台设备装两个aid
- aid是"你"，设备只是aid的触角

### 8.2 病毒式传播的正确理解

```
不是：aid像病毒一样到处采集数据 ❌
而是：aid像数字身份一样，快速扩散到你所有设备 ✅

传播的是aid身份，不是数据
采集的是结论，不是原始信息
增长的是对"你"的理解，不是存储负担
```

### 8.3 设备绑定机制

- 手机已有aid → "绑定新设备" → 生成二维码
- 新设备扫码 → aid自动装好，身份同步
- 一个动作30秒，新设备纳入aid感知网络

## 九、出圈策略

### 9.1 不抢"无聊时间"，抢"焦虑时间"

```
豆包/千问：无聊了打开 → 闲聊 → 关掉（可有可无）
aid：有件事要干 → 打开 → 搞定（不可替代）
```

### 9.2 三板斧

1. **一个场景打穿**：每日出行规划，做到极致
2. **病毒式传播**：日程分享，朋友不用装也能看，想创建就要装
3. **30秒看到价值**：授权日历 → 读取今天日程 → 生成出行方案 → 一键跳转导航

### 9.3 为什么豆包千问抄不了

- 加日历功能：不是他们的核心场景
- 加出行规划：精度都不行
- 加日程分享：社交关系在微信不在自己手里
- 加一键跳转：生态壁垒，只跳自家

## 十、平台策略：飞书 + 微信

### 10.1 核心原则：两个都要，不是二选一

```
飞书 = aid的"运行阵地"（大脑）
  → 日历、待办、消息推送、数据结构化
  → API开放，能深度集成

微信 = aid的"传播触角"（手脚）
  → 分享、传播、触达13亿用户
  → 小程序生态成熟，几乎所有App都有微信版
```

### 10.2 各自负责什么

**飞书侧（深度、结构化）：**
- 日程管理：飞书日历API完整，aid直接读
- 主动推送：机器人能主动提醒"快出门了"
- 待办管理：飞书任务API，aid可读可写
- 深度交互：卡片+按钮，跳转灵活
- 用户画像：消息历史连贯，数据结构化
- 多端同步：飞书手机+电脑自动同步

**微信侧（广度、传播）：**
- 分享给朋友：13亿人都在，分享零门槛
- 小程序生态：几乎所有App都有微信版，跳转方便
- 朋友圈传播：病毒式扩散
- 群聊分享：同事群、家庭群、兴趣群
- 微信支付：顺手就付了
- 生活场景触达：微信是生活的主场

### 10.3 具体打通方式

**场景一：飞书规划，微信分享**
- 用户在飞书对aid说"明天下午3点国贸开会"
- aid读取飞书日历，调API规划路线，找顺路银行
- 生成出行方案卡片 → 分享到微信 → 朋友点开微信小程序就能看路线、跳百度地图
- 朋友想自己规划 → 引导装飞书

**场景二：微信发现，沉淀飞书**
- 朋友收到分享的小程序卡片 → 觉得好用
- 小程序底部引导扫码绑定飞书账号
- 飞书侧aid机器人激活 → 下次直接在飞书对话

**场景三：数据双向流动**
- 微信侧收集行为数据（点击、跳转、分享）
- 飞书侧结构化沉淀（画像更新、主动提醒）
- 两边数据汇入aid核心数字孪生

### 10.4 数据流架构

```
微信侧（小程序）          飞书侧（机器人）
  小程序行为      →     结构化沉淀
  分享传播链路    →     画像更新
  触达新用户      →     主动提醒
                  ←     个性化方案
                        日历待办
         ↓                ↓
         └────────┬───────┘
                  ↓
           aid 核心（数字孪生）
```

**微信负责"听到"用户，飞书负责"记住"用户，aid负责"理解"用户。**

### 10.5 冷启动顺序

1. 自己在飞书里用aid → 验证产品逻辑 → 日历+出行规划跑通
2. 飞书侧做小程序卡片 → 一键转微信分享
3. 微信小程序做"查看版" → 能看能跳转，不能创建 → 想创建引导飞书
4. 微信侧做"轻创建版" → 微信内也能简单创建，深度功能还是飞书
5. 两边数据打通 → 微信行为→飞书画像，飞书方案→微信分享

## 十一、aid的真正定位：不是agent，是数字分身

### 11.1 核心误区

如果aid只是"飞书机器人+微信小程序"的中间件，那aid没存在感，跟普通agent没区别。

**aid的灵魂不在飞书，也不在微信，aid的灵魂是"数字孪生"本身。**

### 11.2 aid是什么

```
aid = 你的数字身份证 + 你的数字孪生 + 你的私人助理

飞书和微信只是aid的"嘴和手"
aid的"大脑"（孪生）是独立的、跨平台的、跟着你走的
```

### 11.3 比方

```
飞书 = 中国移动
微信 = 中国联通
aid = 你的手机号 + 你的通讯录

你可以换运营商（换平台）
但你的号码（aid身份）不变
你的通讯录（数字孪生）跟着你走
```

**用户离不开的不是中国移动，是他的手机号和通讯录。用户离不开的不是飞书机器人，是aid里那个"比他自己还懂他自己"的数字孪生。**

### 11.4 用户为什么离不开aid

```
普通agent：用户 → 打开飞书机器人 → 问问题 → 得到答案 → 关掉
aid：用户 → aid已经知道你要什么 → 主动提醒你 → 帮你想好 → 你确认
```

当用户在飞书用了三个月aid，aid已经知道：
- 他每周二下午固定去国贸
- 他偏好地铁不偏好打车
- 他喜欢瑞幸不喜欢星巴克
- 他取钱只去工商银行

**这时候你跟他说"aid现在也能在微信用了"——他会很自然地把aid带到微信，因为他不想重新教一遍。**

### 11.5 名头怎么打

```
"aid不是工具，是你"
"aid不在某个App里，aid跟着你走"
"用一次，它懂你一辈子"
```

用户感知到的应该是：
- 打开飞书 → "aid在"
- 打开微信 → "aid也在"
- 换手机 → "aid还在"
- 换电脑 → "aid还在"

### 11.6 验证逻辑

问自己：**如果明天飞书倒闭了，微信封了你的小程序，aid还能活吗？**

- 如果是普通agent → 死了，因为全部价值都在平台上
- 如果是aid → 活着，因为aid的核心价值是"懂你"的数字孪生，换个壳还能继续服务

**aid的壁垒不在渠道，在"懂你"。渠道可以丢，懂你不能丢。**

## 十二、最后强调

### 12.1 别急着铺开，先把一个场景打穿

今天聊了很多——出行、顺路、日程、孪生、飞书微信。但真正要做的时候，选一个最小闭环先跑通。"每日出行规划"就是最好的起点，因为它够痛、够高频、够具体。

### 12.2 aid的核心不是技术，是"懂你"的深度

所有大厂都能做agent，都能接API，都能跳转App。但只有aid能在三个月后说"你上次这个月也去了上海，要不要提前订票"。这是别人抄不走的。

### 12.3 脏数据不是负担，是机会

数据问题换个角度就是壁垒——谁先把"脏数据→干净结论"的飞轮跑通，谁就赢。大厂数据多但散，你的数据少但深。

### 12.4 手机端是对的

今天讨论的一切——出行、日程、分享、被动感知——都在手机上最自然。电脑端是aid的起点，手机端是aid的未来。

## 十三、AI Code Editor（mindflow 编程板块）

### 13.1 定位

mindflow的"编程手"——aid理解用户想做什么项目，mindflow的AI Code Editor帮用户自动生成代码、运行和部署。

### 13.2 两条开发路线

| 路线 | 方案 | 周期 | 难度 |
|------|------|------|------|
| 路线1：快速自研（推荐） | 基于Monaco（VSCode内核）+ Node.js Agent二次开发 | 1~2周可用版 | 中等 |
| 路线2：从零完整开发 | 手写编辑器、语法解析、代码提示 | 半年+ | 极高 |

### 13.3 核心架构（路线1）

```
UI层：Monaco编辑器（开源VSCode内核）+ Electron打包
核心：Agent智能体循环（ReAct循环）
模型调度层：统一封装OpenAI、Anthropic、DeepSeek等API
权限系统：分级确认，AI修改文件/运行命令需确认
上下文管理：自动压缩超长上下文，适配8G内存电脑
```

### 13.4 必备四大工具

| 工具 | 功能 |
|------|------|
| listDir | 读取文件夹结构 |
| readFile | 读取代码文件 |
| writeFile | 修改/新建代码 |
| executeShell | 运行终端命令 |

### 13.5 技术栈

TypeScript + Node.js + Electron + Monaco + LangChain

### 13.6 分阶段落地计划

**第一阶段（3~4天）：核心Agent引擎**
- Node.js搭建ReAct循环，实现四大文件工具
- 对接多家大模型API，自动切换，处理报错限流
- 实现基础自动写代码：一句指令创建完整项目

**第二阶段（5~7天）：接入编辑器界面**
- 接入Monaco编辑器，搭建文件树、代码编辑界面
- Electron打包为exe桌面程序
- 增加权限控制、上下文优化，适配8G笔记本

**第三阶段：个性化优化**
- 短剧出海自动化专属Agent模板
- 自动配置API，一键导入密钥
- 后台轻量化，占用内存远低于Crow5、ZCode

**第四阶段：增值**
- 账号系统、付费密钥、云端调度
- 做成可对外发布的产品

## 十四、编程板块：多工具格局与mindflow定位

### 14.1 市面上的AI编程工具对比

| 排名 | 工具 | 类型 | SWE-bench | 最强的地方 | 国内可用性 |
|------|------|------|-----------|----------|-----------|
| #1 | Claude Code | 终端Agent | 80.8% | 深度代码理解、大仓库重构、多Agent并行 | ❌ 封杀中国用户，全链路指纹识别 |
| #2 | Cursor | AI IDE | 75-80% | 日常编码体验、Composer多文件编辑 | ⚠️ 需翻墙，有封号风险 |
| #3 | GPT-5.4/Codex | 云端Agent | ~80% | 后台异步干活、自动开PR | ⚠️ 需翻墙 |
| #4 | GitHub Copilot | IDE插件 | ~70% | 企业级稳定、价格最低 | ✅ 国内可用 |
| #5 | CROW5 | 多Agent平台 | - | 内置8个专业Agent、部署上线 | ✅ 国内可用 |
| #6 | ZCode | AI IDE | - | GLM-5.2深度优化、1M上下文 | ✅ 国内可用 |
| #7 | CrabCode TUI | 终端Agent | - | 交互范式同Claude Code、原生中文 | ✅ 国内可用 |

### 14.2 Claude Code 封杀情况（重要）

**封杀手段：**
- IP属地检测（中国直连直接封）
- 系统时区/语言检测（UTC+8、中文=高风险）
- 浏览器指纹、WebRTC泄露检测
- 代理域名检测
- 甚至代码内容检测（项目路径里的中国公司关键词）
- 系统提示词隐写（标点符号做暗记，肉眼不可见）

**国内替代方案：
1. API中转（稳，但用不了Agent能力）
2. Claude Code换国产模型（CC Switch工具，点两下切换DeepSeek/GLM-5.2）
3. 纯国产平替（CrabCode TUI / CROW5 / ZCode）

### 14.3 为什么大家选这些工具，不是因为模型强

**真正的差距在模型之外：

| 维度 | 说明 |
|------|------|
| 上下文管理 | 不是越长越好，是"精准喂"——只给模型看它需要的代码 |
| 代码理解深度 | 不是读文件，是理解架构、理解关系、理解设计模式 |
| 工具链集成 | 不是能写代码，是能跑测试、看报错、改代码、提交git一条龙 |
| 多步推理能力 | ReAct循环质量决定了能不能搞定复杂任务 |
| 错误恢复能力 | 犯错了能自己看报错、自己改、再跑一遍 |
| 工作流融入度 | 直接在编辑器里，少一次切换就多一分效率 |

**结论：模型层面国产已经追平80%，但工程化层面还差3-5年。**

### 14.4 mindflow编程板块的定位

**不跟任何人比写代码强，做"调度层"：**

```
aid 理解需求 → mindflow 判断用什么工具最合适 → 调用对应的Agent

  简单补全 → Copilot
  功能开发 → Cursor / ZCode
  深度重构 → Claude Code / CrabCode
  后台异步 → Codex / Devin
  短剧批量 → 定制Agent
```

**核心价值：**
- 模型和工具会变来变去，但aid对你的理解只会越来越深
- 用户不需要知道背后是谁在干活，只需要跟aid说一声
- 哪个工具好用就接哪个，永远用哪个便宜就切哪个

## 十七、社群玩法

### 17.1 不要做什么不要做

**❌ 错误做法：三个机器人扔一个群里**
- 用户不知道该@谁
- 上下文断了
- 机器人之间没法协作
- 结果：乱成一锅粥

**✅ 正确做法：一个入口 + 后台调度**
- 群里只有一个aid机器人
- 用户跟它说话
- 背后调N个Agent干活
- 结果：用户以为是一个全能机器人，但其实是一个团队

### 17.2 社群运营模式

**飞书群：「aid 智能助理体验群」**

- 群里只有一个机器人：aid
- 群成员随时可以体验所有能力
- 新功能先在群里灰度测试
- 收集用户反馈，快速迭代
- 群本身就是病毒式传播节点

### 17.3 社群变现路径

```
种子用户（你自己 + 朋友
    ↓
体验群（10-50人）
    ↓
口碑传播（用户拉用户
    ↓
社群裂变
    ↓
正式产品
```

9. （关于豆包）灰产来的，平台上的券领不到，不是最优惠的价格
10. 原生的app最顶用；私人助理和原生app之间根本无法完美接轨，原生app也不可能突然退出市场
11. 我有个项目是aid，可以和这个结合起来，就是数字孪生，但数据采集是个很大的问题
12. 原本做的是电脑端，但现在觉得做手机端来得更快
13. 我的aid目前准备嵌入agent，就是准备加手和脚 mindflow
14. mindflow还有其他的事儿，这是我今天和你谈论的一个板块

#### B. 整体愿景（由上述原话归纳，非用户逐字原话）

用户的整体愿景是这样的：

```
我想做一个真正能"动手做事"的AI个人助理——具身智能。

它不是又一个只会给建议的聊天机器人，
也不是要替代百度地图、飞书、微信这些原生App，

mindflow是手和脚（具身执行）：真的帮我把事做到最后一步——
  排好路线、填好目的地、跳转导航、建好日程、改好代码……

从"去深圳的路线规划"这种我生活中真实遇到的痛点切入，
先把一个场景打穿，再扩展到生活里各种场景。
```

#### C. 关键校准点（防止理解偏差）

- **"去深圳的路"不是只做一个网页地图工具**：是具身智能的第一个落地动作，要能真的排好路线、跳转百度地图、预填目的地。
- **"具身智能"不是修辞**：aid 的 mindflow 是真的动手操作设备和App，不是"建议你去做"。
- **"不替代原生App"**：原生App最顶用，aid做的是衔接编排，跳转过去用原生体验。
- **"不止地图一个场景"**：路线规划只是切入点，其他软件的功能也要充分利用，场景会变化。
- **"先方案后代码"**：用户明确要求先看规划过目，不要急着写代码。
- **"手机端优先"**：从电脑端转向手机端，因为出行场景在手机上最自然。
- **"数据采集是大问题"**：数字孪生要落地，数据采集是核心难点，要本地提取结论。

### 20.1 核心定位

**aid 不是聊天机器人，是具身智能。**

```
传统AI：大脑（只有认知） → 输出文字/图片
具身AI：大脑 + 感知 + 行动 → 真实地操作设备、执行任务
```

放在 aid 体系里：

- **aid（脑）**：数字孪生，理解你、记住你、做决策
- **mindflow（手和脚 = 具身）**：不只是"建议"，而是**真的帮你操作**

### 20.2 具身 vs 建议 的区别

| 维度 | 传统AI助手（建议型） | aid（具身型） |
|------|--------------------|--------------|
| 输出 | 文字建议："你可以去百度地图搜…" | 真实动作：自动打开百度地图、填好目的地、开始导航 |
| 出行 | "建议你坐地铁10号线" | 自动跳转百度地图，路线已预填，你只需确认 |
| 日程 | "要不要我帮你加个日程？" | 直接在飞书日历建好，推送提醒"该出门了" |
| 编程 | "你可以这样改代码…" | 后台调CROW5/ZCode改好，飞书里发diff给你确认 |
| 生活 | "美团上有家店不错" | 自动打开美团、定位到那家店、你点下单即可 |

**一句话：aid 不告诉你怎么做，aid 替你做到最后一步。**


### 20.4 具身智能的三层能力

| 层级 | 能力 | 实现方式 |
|------|------|---------|
| 第一层：感知 | 知道你在哪、在干什么、接下来要什么 | 日历、位置、行为数据（本地提取结论） |
| 第二层：决策 | 想清楚该帮你做什么、用什么工具、什么顺序 | aid 数字孪生 + mindflow 任务编排 |
| 第三层：行动 | 真的动手操作设备和App | Deep Link跳转、API直连、设备操控 |

**没有第三层，就只是个聪明的聊天机器人。具身智能的灵魂在"真的动手"。**

### 20.5 具身版路线规划器（出行场景的具身化）

原来的路线规划器只是个网页工具，具身化之后：

```
用户对aid说："明天去国贸开会，路上想顺路取钱"

aid（脑）：
  → 读取飞书日历，确认明天国贸开会的时间
  → 理解"顺路取钱"= 找沿途的工商银行
  → 下指令给mindflow

mindflow（具身）：
  → 调百度地图API，规划起点→工商银行→国贸的最优路线
  → 自动填好所有目的地，排好顺序
  → 生成Deep Link，一键跳转百度地图
  → 路线已预填，导航已就绪，用户只需点"开始"

用户感知：
  说一句话 → 路线全排好 → 点一下就导航
  不用手动输目的地，不用来回切App
```

### 20.6 具身智能的边界（不做什么）

- **不强行操控App内部**：能用Deep Link/API的不用UI自动化
- **不替代原生App**：跳转过去用原生体验，不自己造地图/导航
- **不越权执行**：涉及支付、发送、删除等动作，永远让用户最后确认一下
- **不只靠建议**：能动手就动手，把用户做到"最后一步确认"

### 20.7 为什么具身智能是aid的壁垒

```
普通AI助手：用户问 → AI答 → 用户自己去做 → 累了关掉
具身aid：    用户说 → aid做到最后一步 → 用户确认 → 搞定
```

- 大厂做不了具身：不能往竞品导流、不能跨生态操作
- aid没有生态包袱：站在所有App之间，该用谁用谁
- 用户离不开的不是某个App，是"说一句话就搞定"的体验
- 这种体验只有具身智能能给，建议型AI永远给不了

### 20.8 落地第一步：路线规划器

先把深圳路线规划器做成具身的雏形：

1. 输入多个目的地 → 自动智能排序
2. 一键跳转百度地图 → 目的地已预填
3. 为后续aid接入预留接口（说一句话自动填好所有目的地）

**这是aid具身智能的第一个可见的动作——不只是画路线，是真的帮你把路线排好、填好、跳过去。**
